## ১. লক্ষ্য (ব্যবহারকারীর মূল চাওয়া)

সাইটটা মাল্টি-টেন্যান্ট — একাধিক প্রতিষ্ঠান এখানে সফটওয়্যার ব্যবহার করবে।
তাই প্রতিটা প্রতিষ্ঠান যেন:
1. **কোম্পানির (madrasah-website অপারেটরের) সাথে যোগাযোগ ছাড়াই** নিজেরা
   নিজেদের হাজিরা ডিভাইস কানেক্ট করতে পারে, এবং
2. **নিজেরাই নিজেদের ছাত্রদের ফিঙ্গারপ্রিন্ট/কার্ড এনরোল** করতে পারে —

— দুটোই নিজের প্রতিষ্ঠানের অ্যাডমিন প্যানেল থেকে সরাসরি, কোনো raw API
কল/Postman/টেকনিক্যাল ধাপ ছাড়া।

## ২. এখন কী আছে, কী নেই (`ATTENDANCE_DEVICE_PLAN.md` থেকে যাচাই করা)

| জিনিস | অবস্থা |
|---|---|
| `attendance_devices`/`attendance_logs` টেবিল, `students.fingerprintId`/`cardUid` কলাম | **আছে** (DB স্কিমায়, Phase 1) |
| ডিভাইস ম্যানেজমেন্ট API (`server/src/routes/attendanceDevices.js`: `GET/POST/PUT/regenerate-secret`, `requirePermission("attendance")`) | **আছে**, কিন্তু কোনো UI পেজ থেকে কল হয় না |
| ডিভাইসের পাবলিক পাঞ্চ API (`POST /api/device/punch`, `GET /api/device/latest-punch/:deviceId`) | **আছে**, multi-tenant subdomain-স্কোপড, tenant-নিরপেক্ষভাবেই কাজ করে (কোনো পরিবর্তন লাগবে না) |
| কিয়স্ক মনিটর পেজ (`/kiosk/:deviceId`) | **আছে** |
| জেনেরিক `hardware-bridge/` (push/ADMS প্রোটোকল) | **আছে**, কিন্তু আসল হার্ডওয়্যার ছাড়া অপরীক্ষিত, node+npm লাগে চালাতে |
| ছাত্র প্রোফাইল ফর্মে `fingerprintId`/`cardUid` ইনপুট ফিল্ড | **নেই** |
| ডিভাইস অ্যাড/লিস্ট/সিক্রেট-দেখার অ্যাডমিন UI পেজ | **নেই** |
| স্ক্যান করে সরাসরি ফিল্ড বসানোর এনরোলমেন্ট মোড | **নেই** |
| bridge-এর সহজ (নন-টেকনিক্যাল) সেটআপ/ইনস্টলার | **নেই** |
| বাংলা ধাপে-ধাপে সেটআপ গাইড (ইন-অ্যাপ বা ডক) | **নেই** |

**সংক্ষেপে:** আর্কিটেকচারের দিক থেকে self-service ইতিমধ্যে সম্ভব (device
request প্রতিষ্ঠানের নিজের subdomain-এ যায় বলে স্বয়ংক্রিয়ভাবেই সেই
প্রতিষ্ঠানের schema-তে স্কোপ হয়, কোম্পানির কোনো ম্যানুয়াল ধাপ লাগে না) —
বাধাটা শুধু **UI-এর অভাব**।

## ৩. মূল অ্যাসাম্পশন ও সিদ্ধান্ত — শুরুর আগে কনফার্মেশন দরকার

- **এনরোলমেন্ট-মোডের ডিজাইন (Phase 2C-এর জন্য জরুরি):** "স্ক্যান করে
  বসান" বাটনে ক্লিক করলে অ্যাডমিন যে ছাত্রের প্রোফাইল এডিট করছেন, তার
  জন্য একটা নির্দিষ্ট ডিভাইস বেছে নিতে হবে (ড্রপডাউনে প্রতিষ্ঠানের
  বিদ্যমান ডিভাইসগুলো থেকে), তারপর ৩০ সেকেন্ড ধরে
  `GET /api/device/latest-punch/:deviceId` পোল করে সর্বশেষ scan-টা
  ধরবে। এই স্ক্যানটা **সত্যিকারের পাঞ্চ ইভেন্ট হিসেবেই গণনা হবে**
  (attendance_logs-এ ইনসার্ট হবে, ম্যাচ না পেলে আজকের attendance-এ কোনো
  প্রভাব পড়বে না যেহেতু ছাত্র খুঁজেই পাওয়া যায়নি) — এনরোলমেন্টের জন্য
  আলাদা কোনো "সাইলেন্ট" মোড ডিভাইসে বসানো লাগবে না, এটা এখনকার প্ল্যানের
  ইচ্ছাকৃত সরলীকরণ। ভুল বোঝাবুঝি এড়াতে ঠিক কিনা এই ধাপেই কনফার্ম করা
  দরকার।
- **raw identifier এক্সপোজ করা:** বর্তমান `GET /device/latest-punch/:deviceId`
  রেসপন্স unmatched স্ক্যানে `matched:false, student:null` দেয়, কিন্তু
  কোন raw fingerprintId/cardUid স্ক্যান হয়েছিল সেটা ফেরত দেয় না (যদিও
  `attendance_logs.identifier` কলামে সেভ হয়, Phase 2/4 ফিক্স থেকে)।
  এনরোলমেন্ট-মোডের জন্য এই raw identifier স্টাফ-অথেনটিকেটেড কোনো
  এন্ডপয়েন্ট থেকে ফেরত পাওয়া দরকার — এটা পাবলিক kiosk-facing এন্ডপয়েন্ট
  থেকে না দিয়ে **নতুন, authenticated, `attendance`-permission-গার্ডেড**
  একটা এন্ডপয়েন্ট দিয়ে করা হবে (নিচে Phase 2C দেখুন), যাতে kiosk পাবলিক
  পোলিং থেকে কেউ অন্য ছাত্রের raw ফিঙ্গারপ্রিন্ট আইডি "শুনতে" না পারে।
- **hardware-bridge প্যাকেজিং (Phase 3B):** সত্যিকারের `.exe`
  ইনস্টলার বানাতে (`pkg`/`nexe`-জাতীয় টুল) একটা নতুন **dev-dependency**
  লাগবে (`hardware-bridge/`-এর নিজস্ব `package.json`-এ, মূল
  root/client/server-এর না — তাই AGENTS.md Rule 5-এর "মূল অ্যাপে নতুন
  dependency" নিয়মটা টেকনিক্যালি প্রযোজ্য না, কিন্তু নীতিগতভাবে একই
  কারণে আগেই জানিয়ে রাখা হচ্ছে)। এছাড়া **`.exe` বানিয়ে আসলে চালিয়ে
  দেখা এই sandbox-এ সম্ভব না** — Windows বিল্ড/টেস্ট আপনার নিজের মেশিনে
  লাগবে। তাই Phase 3 দুই ভাগে (3A সহজ UX উন্নতি, কোনো নতুন dependency
  ছাড়াই; 3B আসল exe প্যাকেজিং, dependency + আপনার মেশিনে টেস্ট লাগবে) —
  3B শুরুর আগে আলাদাভাবে কনফার্ম করে নেওয়া হবে।
- **সেটআপ গাইডে ছবি/স্ক্রিনশট (Phase 4B):** sandbox-এ আসল অ্যাপ চালিয়ে
  স্ক্রিনশট নেওয়া সম্ভব না। তাই "ধাপে ধাপে ছবি সহ" আক্ষরিক স্ক্রিনশট না
  হয়ে **নাম্বার করা ধাপ + কোন বাটন/মেনুতে ক্লিক করতে হবে তার স্পষ্ট
  বর্ণনা + ছোট আইকন/ডায়াগ্রাম (বিদ্যমান lucide আইকন দিয়ে)** — এটা
  ঠিক আছে কিনা, নাকি ব্যবহারকারী নিজে বাস্তব স্ক্রিনশট পরে বসিয়ে দেবেন
  (গাইড পেজে placeholder জায়গা রেখে) সেটা Phase 4 শুরুর আগে কনফার্ম
  করা দরকার।
- **Permission:** ডিভাইস-ম্যানেজমেন্ট পেজ ও এনরোলমেন্ট-মোড দুটোই
  বিদ্যমান `"attendance"` permission-ই ব্যবহার করবে (ATTENDANCE_DEVICE_PLAN.md-এর
  আগের সিদ্ধান্ত অনুযায়ী — নতুন permission bucket লাগবে না, `attendanceDevices.js`-এর
  ব্যাকএন্ড ইতিমধ্যেই এভাবে গার্ডেড)।

ভুল মনে হলে **"শুরু কর" বলার আগে** জানাবেন — সংশোধন এই ধাপেই সহজ।

## ৪. কাজ ৪টা Phase-এ — বড়গুলো sub-phase-এ ভাগ করা

### Phase 1 — ডিভাইস-ম্যানেজমেন্ট অ্যাডমিন পেজ (শুধু ফ্রন্টএন্ড, ব্যাকএন্ড রেডি)

**সাব-ফেজ 1A — API + টাইপ ওয়্যারিং**
- `client/src/types/index.ts` — নতুন `AttendanceDevice { id, deviceId,
  name, location, active, createdAt }` + `AttendanceDeviceCreateResponse`
  (উপরেরটা + একবারই আসা `secretKey`)।
- `client/src/lib/api.ts` — নতুন `api.attendanceDevices` নেমস্পেস:
  `list()`, `create({deviceId, name, location})`, `update(id, {name,
  location, active})`, `regenerateSecret(id)` — `attendanceDevices.js`
  ব্যাকএন্ডের চারটা এন্ডপয়েন্টের সরাসরি ওয়্যারিং, নতুন কোনো ব্যাকএন্ড
  কোড লাগবে না।

**সাব-ফেজ 1B — UI পেজ + রাউটিং + সাইডবার + i18n**
- নতুন `client/src/modules/AttendanceDevices.tsx` — লিস্ট টেবিল
  (deviceId/name/location/active টগল), "নতুন ডিভাইস" ফর্ম (deviceId +
  name + location), তৈরি হওয়ার পর **একবারই দেখানো** secretKey একটা
  মোডালে (কপি বাটনসহ, "এই কী আর দেখানো হবে না, এখনই কপি/লিখে রাখুন"
  সতর্কবার্তা — regenerate-secret বাটনও একই মোডাল রিইউজ করবে)।
  শুধু `components/ui/` (`Card`/`Field`/`Input`/`Select`/`Button`/`Badge`)
  ব্যবহার হবে, কোনো raw `style={{}}` না (AGENTS.md ডিজাইন-সিস্টেম রুল,
  নতুন ফাইল বলে ছাড় নেই)।
- `client/src/App.tsx` — নতুন `lazy()` রুট `attendance-devices`
  (বিদ্যমান প্যাটার্নে)।
- `client/src/components/Sidebar.tsx` — নতুন nav আইটেম (`attendance`
  permission-এর আওতায়, "হাজিরা ডিভাইস" লেবেল, নতুন আইকন key — যেমন
  `icons.ts`-এ `Fingerprint`/`Scan` lucide আইকন যোগ করে)।
- `client/src/i18n/bn.ts` + `en.ts` — নতুন `attendanceDevices` ব্লক
  (টাইটেল, ফর্ম লেবেল, সতর্কবার্তা, খালি-স্টেট) দুই ফাইলেই key-parity
  বজায় রেখে।
- **টেস্ট:** `npm run check` (lint+typecheck+build) + ম্যানুয়ালি একটা
  টেস্ট ডিভাইস অ্যাড করে দেখা secretKey একবারই দেখাচ্ছে কিনা, regenerate
  কাজ করছে কিনা।

### Phase 2 — ছাত্র প্রোফাইলে fingerprintId/cardUid + এনরোলমেন্ট মোড

**সাব-ফেজ 2A — ব্যাকএন্ড: ছাত্র create/update-এ ফিল্ড দুটো গ্রহণ**
- `server/src/routes/students.js` — `INSERT_COLUMNS`/`UPDATE_COLUMNS`-এ
  `['"fingerprintId"', "fingerprintId"]`, `['"cardUid"', "cardUid"]` যোগ
  (বিদ্যমান প্যাটার্নেই, ঠিক `birthRegistrationNumber`-এর পাশে)।
  `duplicateError()`/`constraintError()`-এ এই দুই কলামের জন্যও চেক যোগ
  (Phase 1 SQL-এর partial unique index-এর সাথে মিলিয়ে, বার্তা: "এই
  ফিঙ্গারপ্রিন্ট আইডি ইতিমধ্যে অন্য ছাত্রের সাথে যুক্ত")।
- `server/src/models/studentAdmission.js` (`admissionFromBody`/
  `validateAdmission`/`RETURNING_COLUMNS`/`LIST_COLUMNS`) — এই দুই ফিল্ড
  ঐচ্ছিক (optional, খালি রাখা যাবে) হিসেবে যোগ, কোনো validation বাধ্যতামূলক
  না (সব ছাত্রের ডিভাইস এনরোলমেন্ট লাগবে না)।
- **টেস্ট:** `npm run check` + একটা টেস্ট ছাত্র বানিয়ে/আপডেট করে ফিল্ড
  দুটো সেভ হচ্ছে কিনা, ডুপ্লিকেট দিলে ঠিক এরর আসছে কিনা।

**সাব-ফেজ 2B — ফ্রন্টএন্ড: সাধারণ (ম্যানুয়াল টাইপ) ফিল্ড**
- `client/src/types/index.ts` — `Student`/`StudentAdmission` টাইপে
  `fingerprintId?`/`cardUid?` যোগ।
- `client/src/modules/Students.tsx` (বা যেই ফাইলে ছাত্র-এডিট ফর্ম আছে) —
  নতুন সেকশন/দুইটা `<Input>` (fingerprintId, cardUid), বিদ্যমান
  ফর্ম-গ্রিড প্যাটার্নে বসানো — এই ধাপে শুধু ম্যানুয়াল টাইপ-করে-বসানো,
  স্ক্যান-মোড এখনো না (2C-তে)।
- **টেস্ট:** `npm run check` + ম্যানুয়ালি একটা ছাত্রের প্রোফাইলে
  fingerprintId টাইপ করে সেভ করে দেখা।

**সাব-ফেজ 2C — "স্ক্যান করে বসান" এনরোলমেন্ট মোড (নতুন, বড় অংশ)**
- নতুন ব্যাকএন্ড এন্ডপয়েন্ট: `GET /api/attendance-devices/:id/latest-scan`
  (`attendanceDevices.js`-এ, বিদ্যমান `requirePermission("attendance")`-এর
  আওতায়, তাই staff-authenticated) — সর্বশেষ scan-এর raw
  `identifier`/`identifierType`/`punchAt` ফেরত দেয় (matched/unmatched
  নির্বিশেষে) — kiosk-এর পাবলিক `GET /device/latest-punch/:deviceId`
  থেকে **আলাদা**, কারণ ওটা raw identifier কখনো এক্সপোজ করে না
  (ইচ্ছাকৃতভাবে, উপরের ধারা ৩ দেখুন)।
- `client/src/lib/api.ts` — `api.attendanceDevices.getLatestScan(deviceId)`।
- ছাত্র-এডিট ফর্মে fingerprintId/cardUid ইনপুটের পাশে "স্ক্যান করে বসান"
  বাটন — ক্লিকে একটা ছোট মোডাল/ইনলাইন প্যানেল খোলে: (১) ডিভাইস বেছে নিতে
  বলে (dropdown, Phase 1-এর ডিভাইস লিস্ট), (২) "এখন আঙুল/কার্ড স্ক্যান
  করুন" বার্তা + স্পিনার, (৩) ২ সেকেন্ড পোলিং (`getLatestScan`) — নতুন
  `punchAt` (আগের চেয়ে নতুন) পেলে সেই `identifier` স্বয়ংক্রিয়ভাবে
  fingerprintId/cardUid ইনপুটে বসিয়ে মোডাল বন্ধ করে দেয়, (৪) ৩০
  সেকেন্ডে কিছু না পেলে টাইমআউট মেসেজ ("স্ক্যান শনাক্ত হয়নি, আবার
  চেষ্টা করুন")।
- **টেস্ট:** `npm run check` + Phase 1-এর একটা ডিভাইসে curl/Postman
  দিয়ে টেস্ট-পাঞ্চ পাঠিয়ে (আসল হার্ডওয়্যার ছাড়াই) মোডালে ফিল্ড
  অটো-ফিল হচ্ছে কিনা যাচাই — আসল হার্ডওয়্যার হাতে এলে সত্যিকারের স্ক্যান
  দিয়েও।

### Phase 3 — hardware-bridge সহজে চালানোর প্যাকেজ

**সাব-ফেজ 3A — bridge UX উন্নতি (কোনো নতুন dependency ছাড়াই)**
- `hardware-bridge/index.js`/`.env.example` — শুরুতে `.env`-এর প্রতিটা
  ভ্যারিয়েবল (deviceId, secret, API base) missing/blank হলে স্পষ্ট
  বাংলা+ইংরেজি এরর মেসেজ দিয়ে থেমে যাওয়া (এখন থেমে যায় কিনা/ক্র্যাশ
  করে কিনা যাচাই করে দরকার হলে ঠিক করা)।
  স্টার্টআপে একটা "কনফিগারেশন ঠিক আছে, ৪০৪/৪০১ ছাড়া রেসপন্স আসছে কিনা"
  self-check (`MADRASAH_API_BASE`-এ একটা হালকা রিকোয়েস্ট পাঠিয়ে) যোগ,
  যাতে ভুল URL/deviceId সাথে সাথে বোঝা যায়, ডিভাইস কানেক্ট হওয়ার
  অপেক্ষা না করেই।
- README.md সহজ ভাষায় rewrite — অ্যাডমিনকে ধরে নেওয়া হবে না তিনি
  Node.js/npm চেনেন, প্রতিটা কমান্ডের আগে "এটা কী করে" এক লাইনে।
- **টেস্ট:** কোনো `npm run check`-এর আওতায় না (এই ফোল্ডার মূল অ্যাপের
  বাইরে) — আলাদাভাবে `cd hardware-bridge && npm install && npm start`।

**সাব-ফেজ 3B — আসল স্ট্যান্ডঅ্যালোন `.exe` (নতুন dev-dependency, আপনার
কনফার্মেশন লাগবে শুরুর আগে)**
- `hardware-bridge/package.json`-এ `pkg` (বা সমতুল্য) dev-dependency —
  Node.js রানটাইমসহ single-file Windows executable বানানোর জন্য।
- deviceId/secret/API URL কমান্ড-লাইন আর্গুমেন্ট বা .env এর বদলে একটা
  ছোট প্রথমবার-চালু-হলে-জিজ্ঞেস-করা টেক্সট-প্রম্পট (বা ওই exe-এর পাশে
  একটা `config.txt` — অ্যাডমিন Notepad দিয়ে খুলে বসাতে পারবেন) — চূড়ান্ত
  UX এই সাব-ফেজ শুরুর সময় ঠিক হবে।
- **এই সাব-ফেজ পুরোপুরি আপনার Windows মেশিনে বিল্ড+টেস্ট করা লাগবে** —
  sandbox-এ `pkg` দিয়ে ক্রস-বিল্ড করা সম্ভব হলেও আসল `.exe` চালিয়ে
  device/network আচরণ যাচাই করা সম্ভব না।

### Phase 4 — সেটআপ গাইড ডকুমেন্ট/পেজ (বাংলায়, ধাপে ধাপে)

**সাব-ফেজ 4A — ইন-অ্যাপ গাইড পেজ**
- Phase 1-এর `AttendanceDevices.tsx` পেজেই একটা "কীভাবে কানেক্ট করব?"
  বাটন/ট্যাব, অথবা আলাদা রুট (যেমন `/attendance-devices/guide`) —
  সিদ্ধান্ত Phase 4 শুরুর সময়। বিষয়বস্তু: (১) ডিভাইস অ্যাড করা (Phase 1
  স্ক্রিন রেফারেন্স করে), (২) ডিভাইসের ধরন অনুযায়ী দুই পথ — সরাসরি
  URL কনফিগার (bridge ছাড়া) বনাম bridge চালানো (Phase 3), (৩) ছাত্র
  এনরোলমেন্ট (Phase 2B/2C), (৪) কিয়স্ক স্ক্রিন খোলা।
- শুধু `components/ui/` + নতুন `.ds-*`/scoped ক্লাস, নাম্বার-করা ধাপ
  (`<ol>` স্টাইল কার্ড), প্রতিটা ধাপে সংশ্লিষ্ট lucide আইকন।

**সাব-ফেজ 4B — ভিজ্যুয়াল/ছবি**
- ধারা ৩-এর কনফার্মেশন অনুযায়ী: হয় icon-ভিত্তিক ধাপ-ডায়াগ্রাম (কোনো
  নতুন asset লাগবে না), অথবা placeholder ইমেজ-স্লট (ব্যবহারকারী পরে
  নিজের ফোন থেকে স্ক্রিনশট তুলে বসাবেন, upload করার জায়গা/নির্দেশনা
  দেওয়া থাকবে)।
- **টেস্ট:** `npm run check` + ম্যানুয়ালি গাইড পেজ পড়ে যাচাই ধাপগুলো
  Phase 1-3-এর আসল UI-এর সাথে মিলছে কিনা (ভুল স্ক্রিন-রেফারেন্স যেন না
  থাকে)।

## ৫. Phase-এর ক্রম কেন এভাবে

- **Phase 1 আগে** — Phase 2C (এনরোলমেন্ট মোড) ও Phase 4 (গাইড) দুটোই
  ধরে নেয় ডিভাইস অ্যাড করার একটা UI আছে; এটা ছাড়া এনরোলমেন্ট-মোডে
  "কোন ডিভাইস দিয়ে স্ক্যান করছেন" বাছাই করানোর কোনো উপায় থাকবে না।
- **Phase 2 আগে Phase 3-এর — কিন্তু 2A/2B, 2C নয়, 3A-এর সাথে সমান্তরাল
  চলতে পারে** — 2A/2B (ফিল্ড + ম্যানুয়াল এন্ট্রি) স্বতন্ত্র, bridge-এর
  উপর নির্ভর করে না। 2C (স্ক্যান-মোড) টেস্ট করতে কোনো ডিভাইস থেকে
  পাঞ্চ আসা লাগে, কিন্তু সেটা curl/Postman দিয়েই সিমুলেট করা যায় —
  আসল bridge (Phase 3) থাকা বাধ্যতামূলক না।
- **Phase 3 বড় sub-phase দুটোয় ভাগ করা** — 3A (UX টেক্সট/এরর-হ্যান্ডলিং)
  কোনো নতুন dependency লাগে না, ঝুঁকিহীন। 3B (আসল exe) নতুন
  dependency + আপনার মেশিনে বিল্ড লাগে বলে ইচ্ছাকৃতভাবে আলাদা, যাতে
  আপনি চাইলে শুধু 3A দিয়েই থেমে যেতে পারেন (bridge Node.js দিয়েই
  চালানো, শুধু README সহজ) যদি exe বানানো এখন জরুরি মনে না হয়।
- **Phase 4 সবার শেষে** — গাইড লেখা মানে আগের তিন Phase-এর আসল UI/ফ্লো
  রেফারেন্স করা, তাই সেগুলো শেষ না হলে গাইড ভুল/পুরনো স্ক্রিন বর্ণনা
  করতে পারে।

প্রতিটা sub-phase শেষে `npm run check` + আপনার packaged CMD (zip →
extract → npm install (root/client/server) → npm run check → পাস করলে
commit/push, ফেইল করলে থেমে যাবে) — আগের সব ফিচারের মতোই।
