## ১. সমস্যা (ব্যবহারকারীর বর্ণনা থেকে)

প্রতিষ্ঠানে সাধারণত দিনে একাধিক সময়-ব্লক থাকে (যেমন সকাল থেকে দুপুর পর্যন্ত
ক্লাস, দুপুরে বিরতি, তারপর বিকাল থেকে আবার ক্লাস)। এখন প্রশ্ন হলো — কোন
ছাত্র/শিক্ষক/স্টাফ সঠিক সময়ে প্রতিষ্ঠানে প্রবেশ করেছে, কে দেরি করেছে — এটা
বোঝার কোনো ব্যবস্থা প্রজেক্টে নেই, কারণ কোনো "শিফট/সময়সূচি" ধারণাই কোথাও
সংজ্ঞায়িত নেই। শিক্ষক/স্টাফ/ছাত্র সবার জন্য entry time, exit time এবং
এ-জাতীয় তথ্য মেইনটেইন করা দরকার।

## ২. প্রেক্ষাপট — প্রজেক্টে এখন যা আছে (কোড পড়ে যাচাই করা, 2026-08-18)

| শিফট/সময়সূচি/পিরিয়ড — যেকোনো টেবিল | — | **নেই, পুরোপুরি নতুন ফিচার** |
| ক্লাস/জামাতের তালিকা | `lib/classOptions.js` (ফ্ল্যাট লিস্ট) + `lib/classTree.js` (হায়ারার্কি) — দুটোই `settings(key,value)` টেবিলে JSON ব্লব হিসেবে, কোনো নিজস্ব টেবিল নেই | নতুন শিফট-ম্যাপিং এখানেই যুক্ত হবে |

**সংক্ষেপে যা রিইউজ হবে:** ডিভাইস-পাঞ্চ পাইপলাইন (ছাত্র+স্টাফ দুটোর জন্যই
প্রস্তুত), `attendance_logs`-এর raw টাইমস্ট্যাম্প, RBAC/audit/Zod প্যাটার্ন,
class/staff-এর বিদ্যমান কলাম। **নতুন যা লাগবে:** শিফট মাস্টার-ডাটা, ক্লাস↔শিফট
ও স্টাফ↔শিফট ম্যাপিং, entry/exit সময় সংরক্ষণের কলাম, এবং পাঞ্চ-সময়কে
শিফটের সাথে তুলনা করে status ঠিক করার লজিক।

## ৩. মূল ডিজাইন সিদ্ধান্ত (ব্যবহারকারীর সাথে কনফার্ম হয়েছে)

- **শিফট প্রতিষ্ঠানের পক্ষ থেকে (Admin/Super Admin) তৈরি হবে** — প্রতিষ্ঠান
  ঠিক করবে কয়টা শিফট থাকবে এবং প্রতিটা দিনের কোন সময় থেকে কোন সময় পর্যন্ত।
- **একই জামাত/ক্লাসের সবাই এক শিফটে থাকবে** — প্রতি ছাত্র আলাদা করে শিফট
  বাছাইয়ের দরকার নেই। শিফট বরাদ্দ হবে ক্লাস/জামাত-লেভেলে, ছাত্র-লেভেলে না।
- **স্টাফদের ডিভাইস-অ্যাটেন্ডেন্স ইতিমধ্যে আছে** (উপরে §২ দেখুন) — নতুন করে
  বানানো লাগবে না, শুধু তার সাথে শিফট/লেট-লজিক জোড়া লাগবে।
- **এন্ট্রি-টাইম অনুযায়ী status স্বয়ংক্রিয় ঠিক হবে** — দিনের প্রথম পাঞ্চ
  (বা ম্যানুয়াল এন্ট্রি সময়) শিফটের `startTime + graceMinutes`-এর পরে হলে
  `status = 'দেরিতে'`, নাহলে `'উপস্থিত'`। Exit-টাইম status বদলাবে না, শুধু
  রেকর্ড হবে।
- **ম্যানুয়াল ওভাররাইড থাকবে** — শিক্ষক/অ্যাডমিন চাইলে সিস্টেমের বসানো status
  হাতে বদলাতে পারবেন (যেমন এখন যেমন পারেন)।

## ৪. কাজ কয় ভাগে হবে — **৯ ভাগে** (Phase 1 → 9)

প্রতি Phase-এর পর আপনার প্যাকেজড CMD দিয়ে `npm run check` পাস করলেই পরের
Phase-এ যাওয়া হবে (AGENTS.md rule 2)।

### Phase 1 — DB স্কিমা (protected path, `server/sql/supabase_schema.sql`)

```sql
create table if not exists shifts (
  id integer generated by default as identity primary key,
  name text not null,              -- বাংলা লেবেল, যেমন "সকাল শিফট"
  "nameEn" text default '',
  "startTime" text not null,       -- 'HH:MM', ২৪-ঘণ্টা ফরম্যাট
  "endTime" text not null,
  "graceMinutes" integer not null default 0,
  active boolean not null default true,
  "createdAt" text not null
);

-- ক্লাস/জামাত ↔ শিফট ম্যাপিং। classOptions/classTree-এর ক্লাস নিজস্ব টেবিলে
-- নেই (settings-এ JSON ব্লব), তাই class-slug কে key ধরে আলাদা ছোট টেবিল —
-- ক্লাস ডিলিট/রিনেম হলে এখানকার এন্ট্রি এতিম (orphan) হতে পারে, কিন্তু
-- ক্ষতিকর না (শুধু আর কোনো শিফট রেজলভ হবে না, সেই ক্লাসের ছাত্রদের জন্য নিচে
-- §Phase 4-এর ফলব্যাক প্রযোজ্য হবে)।
create table if not exists class_shifts (
  class text primary key,
  "shiftId" integer not null references shifts(id) on delete cascade
);

alter table staff add column if not exists "shiftId" integer references shifts(id) on delete set null;

alter table attendance add column if not exists "entryTime" text;
alter table attendance add column if not exists "exitTime" text;
alter table staff_attendance add column if not exists "entryTime" text;
alter table staff_attendance add column if not exists "exitTime" text;
```

মাল্টি-টেন্যান্ট মোডে আগে থেকে প্রোভিশন করা টেন্যান্টদের জন্য Super-Admin-এর
"run SQL on all tenants" টুল দিয়ে একবার ম্যানুয়ালি চালাতে হবে (আগের সব নতুন
টেবিলের মতোই)।

### Phase 2 — Backend: শিফট CRUD

- `server/src/lib/shiftSchemas.js` (নতুন) — Zod: `shiftCreateSchema`,
  `shiftUpdateSchema` (`startTime`/`endTime` regex `^\d{2}:\d{2}$`,
  `graceMinutes` 0–180 সীমা)।
- `server/src/routes/shifts.js` (নতুন): `router.use(requirePermission("shifts"))`
  — `GET /` (তালিকা), `POST /` (তৈরি), `PATCH /:id` (এডিট/active টগল)।
  হার্ড DELETE নেই প্রথমে (স্টাফ/ক্লাস রেফারেন্স করলে ভাঙবে) — শুধু active
  টগল, `staff.js`-এর প্যাটার্নে।
- `index.js`-এ `/api/shifts` মাউন্ট, authenticated চেইনের ভেতরে।
- `recordAudit()` কল create/update-এ।

### Phase 3 — Backend: ক্লাস↔শিফট ও স্টাফ↔শিফট বরাদ্দ

- `server/src/routes/classShifts.js` (নতুন) বা `settings.js`-এ যোগ —
  `GET /api/class-shifts` (পুরো ম্যাপ), `PUT /api/class-shifts` (বাল্ক
  আপডেট, `classOptions`-এর মতোই একবারে পুরো ম্যাপ পাঠানো/সেভ করা)।
- `staff.js`-এর `staffUpdateSchema`-তে `shiftId` (nullable int) যোগ —
  বিদ্যমান PATCH রুটই ব্যবহার হবে, নতুন এন্ডপয়েন্ট লাগবে না।

### Phase 4 — Backend: স্বয়ংক্রিয় দেরি-গণনা (মূল লজিক)

- নতুন `server/src/lib/attendanceSchedule.js`:
  - `resolveShiftForClass(className)` — `class_shifts` টেবিল থেকে লুকআপ,
    না পেলে `null` (ফলব্যাক: শিফট নির্ধারিত না থাকলে লেট-গণনা স্কিপ, status
    আগের মতোই সবসময় 'উপস্থিত' — এখনকার আচরণ ভাঙবে না)।
  - `resolveShiftForStaff(staffRow)` — `staff.shiftId` সরাসরি।
  - `computeEntryStatus(punchTimeIso, shift)` — শিফট থাকলে
    `startTime + graceMinutes` এর সাথে তুলনা করে `'উপস্থিত'`/`'দেরিতে'`
    রিটার্ন করে; শিফট না থাকলে `'উপস্থিত'` (আগের ডিফল্ট আচরণ)।
- `lib/devicePunch.js` পরিবর্তন (`recordStudentPunch`/`recordStaffPunch`):
  - দিনের **প্রথম** পাঞ্চে: শিফট রেজলভ করে `computeEntryStatus()` কল,
    `attendance`/`staff_attendance`-এ `status` + `entryTime` আপসার্ট (এখনকার
    হার্ডকোড করা `'উপস্থিত'`-এর বদলে)।
  - পরের পাঞ্চে (একই দিনে): শুধু `exitTime` আপডেট, `status`/`entryTime`
    অপরিবর্তিত থাকবে।
- ম্যানুয়াল হাজিরা রুট (`routes/attendance.js`, `routes/staffAttendance.js`)
  **অপরিবর্তিত** — শিক্ষক/অ্যাডমিন এখনো হাতে status বাছতে পারবেন
  (ম্যানুয়াল ওভাররাইড, §৩ দেখুন); চাইলে ঐচ্ছিক `entryTime`/`exitTime` ইনপুট
  ফিল্ড Phase 8-এ UI-তে যোগ হবে, কিন্তু ব্যাকএন্ড ভ্যালিডেশনে এখনই optional
  হিসেবে গ্রহণ করা হবে (`opsSchemas.js`-এর `attendanceRecordSchema`/
  `staffAttendanceRecordSchema`-তে `entryTime`/`exitTime` optional যোগ)।

### Phase 5 — RBAC (protected path, `server/src/config/roles.js`)

- নতুন পারমিশন-কী: `"shifts"`।
- ডিফল্ট গ্রান্ট (প্রস্তাবিত, §৬-এ কনফার্ম করুন): Super Admin `"*"`-এ এমনিতেই
  পায়; Admin-কে `"shifts"` যোগ; বাকিদের না।

  যোগ। `npm run check` স্বয়ংক্রিয়ভাবে `roles.generated.ts` রিজেনারেট করবে।

  (থাকলে) + "কত মিনিট দেরি" ব্যাজ দেখানো; ম্যানুয়ালি মার্ক করার সময় ঐচ্ছিক
  entry/exit টাইম-ইনপুট (Phase 4-এর optional ফিল্ড ব্যবহার করবে)।
- `Kiosk.tsx` (ঐচ্ছিক, নাইস-টু-হ্যাভ) — পাঞ্চের পর "সময়মতো"/"দেরিতে" লেবেল
  দেখানো যদি রেসপন্সে status থাকে।

### Phase 8 — রিপোর্ট

- Reports মডিউলে "দেরিতে আসা"-র তালিকা (তারিখ-রেঞ্জ, ছাত্র/স্টাফ আলাদা ট্যাব),
  বিদ্যমান `exportReports.ts`/`printReport.ts` রিইউজ করে এক্সপোর্ট/প্রিন্ট।

### Phase 9 — যাচাই ও ডকুমেন্টেশন

- CMD দিয়ে `npm run check` (root/client/server install → sync:roles → lint
  → typecheck → build → test:server)।
- ম্যানুয়াল স্মোক-টেস্ট: শিফট তৈরি → ক্লাসে বরাদ্দ → গ্রেস-টাইমের আগে/পরে
  টেস্ট-পাঞ্চ পাঠিয়ে status ঠিক হচ্ছে কিনা → স্টাফের জন্য একই → ম্যানুয়াল
  এন্ট্রি এখনো কাজ করছে কিনা (রিগ্রেশন চেক) → রিপোর্টে সঠিক তালিকা আসছে কিনা।
- `docs/PROJECT_MAP.md`-এ ছোট factual সংযোজন (নতুন টেবিল/মডিউল/পারমিশনের
  নাম)। `docs/CURRENT_TASK.md` এন্ট্রি DONE করা।

## ৫. স্কোপের বাইরে (এই টাস্কে করা হবে না)

- **একই ক্লাসের দিনে একাধিক আলাদা সেশন** (যেমন সকালে এক ক্লাস, বিকালে সম্পূর্ণ
  আলাদা আরেকটা ক্লাস, দুটোরই আলাদা entry/exit দরকার) — প্রথম রাউন্ডে একটা
  ক্লাস = একটা শিফট = দিনে একটা entry + একটা exit। বিরতি-পরবর্তী দ্বিতীয়
  সেশনের জন্য আলাদা এন্ট্রি দরকার হলে সেটা নিচে §৬-এর প্রশ্ন ১, ভবিষ্যতে আলাদা
  Phase/টাস্ক হিসেবে।
- বিদ্যমান পুরনো ম্যানুয়াল "দেরিতে" রেকর্ড রেট্রোঅ্যাকটিভলি রিক্যালকুলেট করা
  হবে না — নতুন লজিক শুধু নতুন পাঞ্চ/এন্ট্রি থেকে কার্যকর হবে।
- দেরিতে-প্রবেশের জন্য আলাদা গার্জিয়ান SMS টাইপ — এই টাস্কে না (§৬ প্রশ্ন ৩)।

## ৬. খোলা প্রশ্ন — শুরু করার আগে কনফার্ম করুন (ডিফল্ট প্রস্তাবসহ)

1. একই জামাতের ছাত্রদের যদি দিনে একাধিকবার (সকাল + বিকাল, দুটো আলাদা ক্লাস)
   আলাদাভাবে entry/exit ট্র্যাক করা লাগে — নাকি প্রথম রাউন্ডে দিনে একটামাত্র
   entry+exit যথেষ্ট? (ডিফল্ট: একটাই, দিনে একবার)
2. স্টাফের শিফট প্রতিষ্ঠানের একটা ডিফল্ট শিফট থেকে শুরু হবে, নাকি নতুন স্টাফ
   তৈরির সময় বাধ্যতামূলকভাবে বাছতে হবে? (ডিফল্ট: ঐচ্ছিক, না বাছলে
   লেট-গণনা স্কিপ হবে সেই স্টাফের জন্য — §Phase 4-এর ফলব্যাক)
3. দেরিতে প্রবেশে গার্জিয়ানকে আলাদা SMS পাঠানো লাগবে কিনা? (ডিফল্ট: না এখনই,
   বিদ্যমান `attendancePunch` নোটিফিকেশন-টাইপই যথেষ্ট)
4. গ্রেস-মিনিট (কত মিনিট পর্যন্ত দেরি ধরা হবে না) প্রতি-শিফটে আলাদা হবে,
   নাকি পুরো প্রতিষ্ঠানে একটাই কমন মান? (ডিফল্ট: প্রতি-শিফটে আলাদা, যেহেতু
   `graceMinutes` কলাম শিফট-টেবিলেই — বেশি নমনীয়)

কিছু না বললে উপরের ডিফল্টগুলো ধরে Phase 1 থেকে শুরু হবে।

## ৭. AGENTS.md / CURRENT_TASK.md সম্পর্কিত নোট

`docs/STAFF_ATTENDANCE_PLAN.md`-এর §৫ ("স্কোপের বাইরে") এ লেখা ছিল "স্টাফ
অ্যাটেন্ডেন্সের জন্য ডিভাইস/ফিঙ্গারপ্রিন্ট ইন্টিগ্রেশন — এই টাস্কের বাইরে" —
কিন্তু কোড পড়ে দেখা গেছে এটা ইতিমধ্যে বাস্তবায়িত (§২ দেখুন)। একইভাবে
`docs/CURRENT_TASK.md`-এর "স্টাফ/শিক্ষক এন্ট্রি" এন্ট্রিতে
"Status: IN_PROGRESS (কোনো Phase এখনো শুরু হয়নি)" লেখা থাকলেও কোডে
`routes/staff.js`/`routes/staffAttendance.js` পূর্ণাঙ্গ বাস্তবায়িত পাওয়া
গেছে। পুরনো দুটো ডকুমেন্টই অপরিবর্তিত রাখা হয়েছে (AGENTS.md-এর "append-only,
পুরনো এন্ট্রি এডিট না করা" নিয়ম অনুযায়ী) — শুধু এখানে নোট করে রাখা হলো, যাতে
পরবর্তী কোনো এজেন্ট বিভ্রান্ত না হয়। আসল কাজ শুরুর সময় (Phase 9) সেই দুই
ডকুমেন্টে সংশোধনী যোগ করার কথা বিবেচনা করা যেতে পারে।

এই ফিচারটাও একটা সম্পূর্ণ নতুন, আলাদা এন্ট্রি হিসেবে `docs/CURRENT_TASK.md`-এ
যোগ হয়েছে (নিচে দেখুন), বাকি সব এন্ট্রি অপরিবর্তিত।
