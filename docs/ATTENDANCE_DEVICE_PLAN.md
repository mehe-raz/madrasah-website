# পরিকল্পনা: ফিঙ্গারপ্রিন্ট/কার্ড ডিভাইস দিয়ে হাজিরা (Attendance Device Integration)

তৈরি: 2026-08-11 · প্রজেক্ট: madrasah-website · স্ট্যাটাস: **শুধু পরিকল্পনা — এখনো কোনো কোড লেখা হয়নি**

---

## ১. এখন কী চাইছেন (সংক্ষেপে)

ফিঙ্গারপ্রিন্ট/কার্ড-স্ক্যান ডিভাইস দিয়ে ছাত্র হাজিরা দিলে সেই ডাটা সরাসরি
সার্ভারে/ওয়েবসাইটে এন্ট্রি হবে (কখন ঢুকল, কখন বের হলো) এবং গার্জিয়ানকে
জানানো হবে। ডিভাইসের উপরে বসানো একটা মনিটরে সাথে সাথে সেই ছাত্রের ছবি,
নাম, ক্লাস, শাখা, রোল দেখাবে — অর্থাৎ ডাটা আগে থেকে এন্ট্রি করা ছিল কিনা
বোঝা যাবে।

## ২. প্রজেক্টে এখন যা আছে (জিপ খুলে যাচাই করেছি)

| unauthenticated/public রুট প্যাটার্ন (নিজস্ব auth + rate-limit, `requireAuth` চেইনের আগে মাউন্ট) | `server/src/routes/publicSignup.js`, `index.js`-এর `/api/public`, `/api/guardian-auth`, `/api/platform` | আছে — ডিভাইস-রাউটও এই প্যাটার্নেই বসবে (JWT/ইউজার-লগইন না, ডিভাইস-কী দিয়ে) |

| ফিঙ্গারপ্রিন্ট/কার্ড/ডিভাইস সম্পর্কিত কোনো কলাম বা টেবিল | `students`, স্কিমার বাকি অংশ | **নেই** |

**সংক্ষেপে:** গার্জিয়ান SMS, অডিট লগ, পারমিশন, Zod ভ্যালিডেশন, public-route
প্যাটার্ন — এই বিল্ডিং ব্লকগুলো রিইউজ হবে। নতুন যা লাগবে: (ক) ডিভাইস ও raw
পাঞ্চ-লগ রাখার স্কিমা, (খ) ডিভাইস-অথ দিয়ে একটা নতুন পাবলিক এন্ডপয়েন্ট, (গ)
কিয়স্ক মনিটর UI + তাতে রিয়েল-টাইম আপডেট পাঠানোর একটা উপায়, (ঘ) হার্ডওয়্যারের
সাথে কথা বলার একটা আলাদা bridge/agent (মূল কোডবেজের বাইরে)।

## ৩. মূল অ্যাসাম্পশন ও সিদ্ধান্ত — শুরু করার আগে আপনার কনফার্মেশন দরকার

- **রিয়েল-টাইম আপডেট: WebSocket না, ২–৩ সেকেন্ড পোলিং।** WebSocket যোগ করলে
  নতুন npm dependency (`ws` বা `socket.io`) লাগবে এবং Express-এর সাথে সার্ভার
  সেটআপ (Google Cloud Console হোস্টিং, upgrade করা কানেকশন হ্যান্ডল করা)
  আরেকটু জটিল হয়। কিয়স্ক স্ক্রিন সাধারণত একটামাত্র ডিভাইসের সাম্প্রতিকতম পাঞ্চ
  দেখালেই যথেষ্ট — তাই AGENTS.md-এর "কোনো নতুন dependency ছাড়া যা আছে তা দিয়ে
  সমাধান করা" নিয়ম অনুযায়ী শুরুতে সাধারণ পোলিং (`GET
  /api/device/latest-punch/:deviceId`, প্রতি ২ সেকেন্ডে) দিয়ে করছি —
  ব্যবহারিকভাবে এটা ইনস্ট্যান্ট-ই মনে হবে। পরে সত্যিকারের ইনস্ট্যান্ট লাগলে
  WebSocket আলাদা কাজ হিসেবে যোগ করা যাবে (নতুন dependency বলে সেটা আলাদাভাবে
  আপনাকে জানিয়ে শুরু হবে)।
- **হার্ডওয়্যার bridge মূল কোডবেজের বাইরে** — একটা ছোট, আলাদা Node.js
  স্ক্রিপ্ট/প্রজেক্ট হিসেবে থাকবে যেটা ডিভাইসের প্রোটোকল (ব্র্যান্ড-নির্ভর)
  বোঝে ও `POST /api/device/punch`-এ ফরওয়ার্ড করে। madrasah-website
  রিপোজিটরির `npm run check`/lint/build এই অংশ ছোঁবে না।
- **এনরোলমেন্ট: ফিঙ্গারপ্রিন্ট/কার্ড ম্যাপিং অ্যাডমিন প্যানেল থেকে হবে** —
  ছাত্র প্রোফাইলে `fingerprintId`/`cardUid` টেক্সট ফিল্ড হিসেবে বসবে (ডিভাইসের
  নিজস্ব এনরোলমেন্ট মেনু থেকে যে আইডি/UID পাওয়া যায় সেটা ম্যানুয়ালি বসাতে
  হবে) — ডিভাইস থেকে সরাসরি এনরোলমেন্ট-সিঙ্ক এই পরিকল্পনার আওতার বাইরে।
- **entry/exit নির্ধারণ: দিনের প্রথম পাঞ্চ = প্রবেশ, শেষ পাঞ্চ = বাহির** (একই
  দিনে একাধিকবার পাঞ্চ করলেও প্রথম ও শেষটাই গণনা হবে) — ডিভাইস নিজে
  in/out বোতাম আলাদা না করলে এই সরল নিয়মেই এগোনো হবে। ডিভাইসে in/out আলাদা
  বোতাম থাকলে সেটা bridge থেকে `direction` ফিল্ডে পাঠানো যাবে, আলাদা লজিক
  লাগবে না।
- **গার্জিয়ান SMS: শুধু "প্রথম পাঞ্চ" (প্রবেশ)-এ পাঠানো হবে**, প্রতি পাঞ্চে
  না — নাহলে একই দিনে বারবার SMS/wallet খরচ হতে পারে। বাহিরের সময়
  (exit) SMS পাঠানো লাগবে কিনা সেটা Phase 3-এ আলাদা `notificationType`
  হিসেবে অপশনাল রাখা হবে, ডিফল্ট বন্ধ (অ্যাডমিন চাইলে SMS সেটিংস পেজ থেকে
  চালু করবেন)।
- **`attendance` টেবিলের বর্তমান আচরণ ভাঙবে না** — শিক্ষকের ম্যানুয়াল
  হাজিরা-মার্কিং যেমন আছে তেমনই থাকবে; ডিভাইস-পাঞ্চ এলে সেই ছাত্রের সেই
  দিনের `attendance.status = 'উপস্থিত'` আপডেট/আপসার্ট হবে (এখনকার
  `ON CONFLICT ("studentId", date) DO UPDATE` লজিকই রিইউজ হবে), যাতে
  ডিভাইস-হাজিরা আর ম্যানুয়াল হাজিরা একই জায়গায় মিলে যায়, দুটো আলাদা সিস্টেম
  হয়ে না যায়।
- **পারমিশন: নতুন "attendance" পারমিশনই যথেষ্ট**, ডিভাইস/কিয়স্ক ম্যানেজমেন্ট
  পেজের জন্য নতুন কোনো permission bucket বানানো লাগবে না বলে ধরছি —
  Admin/Hostel Manager যারা এখন attendance permission রাখেন তারাই ডিভাইস
  অ্যাড/এডিট করতে পারবেন।

ভুল মনে হলে "শুরু কর" বলার আগে জানাবেন — সংশোধন সহজ, এই ধাপেই।

## ৪. কাজ কয় ভাগে হবে — **৫ ভাগে** (Phase 1 → 5)

কেন ৫ ভাগ: (ক) স্কিমা আগে ঠিক না হলে বাকি কিছুই বসানো যাবে না; (খ) ডিভাইস
API-টা প্রথম নতুন *unauthenticated* এন্ডপয়েন্ট এই প্রজেক্টে, তাই এটা একা
আলাদাভাবে টেস্ট হওয়া দরকার নিরাপত্তার দিক থেকে; (গ) SMS হুক ছোট কিন্তু
টাকা/wallet ছোঁয় বলে আলাদা যাচাই দরকার; (ঘ) কিয়স্ক UI স্বতন্ত্র ফ্রন্টএন্ড
কাজ; (ঙ) হার্ডওয়্যার bridge সম্পূর্ণ ভিন্ন পরিবেশ (মূল রিপোর প্রজেক্টের
বাইরে), ব্র্যান্ড-নির্ভর, তাই সবার শেষে। প্রতি ধাপের পর `npm run check` +
আপনার প্যাকেজড CMD দিয়ে যাচাই হবে, পাস না করলে পরের ধাপে যাব না।

### Phase 1 — DB স্কিমা: ডিভাইস, পাঞ্চ-লগ, ছাত্র-ম্যাপিং

- `server/sql/supabase_schema.sql`-এ (protected path — AGENTS.md রুল ৪,
  তাই এই পুরো ফিচারটাই সেই ব্যতিক্রম হিসেবে স্পষ্টভাবে জানিয়ে এগোনো হচ্ছে):
  - `students`-এ: `alter table students add column if not exists
    "fingerprintId" text; alter table students add column if not exists
    "cardUid" text;` + এই দুটোর উপর ইউনিক ইনডেক্স (partial, NULL বাদ দিয়ে —
    বিদ্যমান `admissionNumber`/`birthRegistrationNumber` ইনডেক্সের প্যাটার্নে)
  - নতুন `attendance_devices` টেবিল: `id, "deviceId" (unique text),
    "secretKey" text, name text, location text, active boolean default
    true, "createdAt"`
  - নতুন `attendance_logs` টেবিল: `id, "studentId" (fk → students),
    "deviceId" (fk → attendance_devices), "punchAt" timestamp, direction
    text ('in'/'out'/নাল), method text ('fingerprint'/'card')` — raw
    ইভেন্ট, ডিলিট হবে না, রিপোর্টিং/অডিটের জন্য থেকে যাবে
  - মাল্টি-টেন্যান্ট প্রজেক্ট বলে এই দুই নতুন টেবিলও বাকি সব টেবিলের মতো
    প্রতি-প্রতিষ্ঠান schema-তেই বসবে (কোনো আলাদা ব্যবস্থা লাগবে না,
    `tenantProvision.js` এমনিতেই একই schema ফাইল থেকে নতুন প্রতিষ্ঠান
    বানায়)
- **টেস্ট:** `npm run check` (server syntax) + SQL ফাইলের bracket/সিনট্যাক্স
  ম্যানুয়াল রিভিউ (এই sandbox-এ আসল Postgres নেই বলে schema আসলে চালানো
  আপনার CMD-তেই প্রথম হবে, আগের সব ফিচারের মতোই)।

### Phase 2 — ডিভাইস API (ব্যাকএন্ড, নতুন unauthenticated রুট)

- নতুন `server/src/routes/deviceAttendance.js`:
  - `POST /api/device/punch` — body: `{ deviceId, secretKey, identifier,
    identifierType ('fingerprint'|'card'), timestamp? }`। `deviceId`+
    `secretKey` মিলিয়ে ডিভাইস ভ্যালিডেট, তারপর `fingerprintId`/`cardUid`
    দিয়ে ছাত্র খুঁজে বের করা। মিললে: `attendance_logs`-এ ইনসার্ট,
    দিনের প্রথম পাঞ্চ কিনা চেক করে `attendance` টেবিল আপসার্ট (status
    'উপস্থিত'), প্রথম পাঞ্চ হলে `sendGuardianSms` কল
    (`notificationType: "attendancePunch"`)। রেসপন্সে ছাত্রের
    photo/name/class/section/roll ফেরত দেওয়া হবে (কিয়স্ক পোলিং এন্ডপয়েন্টও
    এই একই ডাটা শেপ ব্যবহার করবে)।
  - `GET /api/device/latest-punch/:deviceId` — ডিভাইস-কী ছাড়া, কিয়স্ক পেজ
    থেকে পোলিং করার জন্য একটা হালকা রেসপন্স (সর্বশেষ পাঞ্চের ছাত্র-ডাটা,
    টাইমস্ট্যাম্প সহ — কিয়স্ক ২ সেকেন্ড পরপর কল করে টাইমস্ট্যাম্প বদলেছে
    কিনা দেখে নতুন পাঞ্চ চেনে)। এটাও public কিন্তু device শুধু আইডি দিয়ে
    রিড করা যায় বলে rate-limit করা দরকার।
  - `index.js`-এ `/api/public`-এর ঠিক প্যাটার্নে (`requireAuth` চেইনের
    আগে) মাউন্ট, নিজস্ব rate limiter (`publicSignup.js`-এর
    `signupLimiter`-এর প্যাটার্নে, কিন্তু বেশি frequent legit ট্রাফিক
    (বহু ছাত্র দিনে বহুবার) ধরে রিজনেবল লিমিট), `tenantResolve.js`-এর
    `isSkippedPath()`-এ যোগ করা লাগবে কিনা — সেটা মাল্টি-টেন্যান্ট রাউটিং
    (কোন প্রতিষ্ঠানের DB) ডিভাইস-রিকোয়েস্টে কীভাবে ঠিক হয় তা `tenantResolve.js`
    পড়ে ঠিক করা হবে (ডিভাইস URL/হেডারে প্রতিষ্ঠান-কোড লাগবে, নাকি
    `deviceId` দিয়েই রেজিস্ট্রি থেকে বের করা যাবে — এটা এই ধাপেই ঠিক হবে)।
  - Zod ভ্যালিডেশন: নতুন স্কিমা `opsSchemas.js`-এ (বিদ্যমান
    `attendanceSaveSchema`-র পাশে) যোগ, বিদ্যমান স্কিমা অপরিবর্তিত।
  - অডিট: `recordAudit()` কল (`action: "attendance.devicePunch"`),
    বিদ্যমান প্যাটার্নে (batch summary না, প্রতি পাঞ্চ একটাই ঘটনা তাই
    per-punch এন্ট্রি ঠিক আছে)।
  - ডিভাইস ম্যানেজমেন্ট রাউট: `server/src/routes/attendanceDevices.js`
    (Admin-only, স্বাভাবিক authenticated `/api` চেইনের ভেতরে,
    `requirePermission("attendance")` দিয়ে) — ডিভাইস অ্যাড/লিস্ট/সিক্রেট
    রিজেনারেট/active টগল।
- **টেস্ট:** `npm run check` + curl/Postman দিয়ে ম্যানুয়ালি একটা টেস্ট পাঞ্চ
  পাঠিয়ে যাচাই (আসল হার্ডওয়্যার ছাড়াই)।

### Phase 3 — গার্জিয়ান SMS হুক

- `server/src/routes/sms.js`-এর `NOTIFICATION_TYPES`-এ `attendancePunch`
  যোগ (settings পেজে টগল করার জন্য) — বিদ্যমান টাইপ-লিস্ট অপরিবর্তিত,
  শুধু একটা নতুন এন্ট্রি।
  বাহিরের (exit) জন্য চাইলে ভবিষ্যতে আলাদা `attendanceExit` টাইপ, এই
  ধাপে ডিফল্ট বন্ধ রেখে শুধু কাঠামোটা রাখা হবে কিনা — ধারা ৩-এর সিদ্ধান্ত
  অনুযায়ী প্রথমে শুধু entry, exit স্কিপ করেই শুরু।
- Phase 2-এর `POST /api/device/punch`-এ যে `sendGuardianSms` কল যোগ হয়েছে
  সেটাই — এই ধাপ মূলত settings-পেজ ইন্টিগ্রেশন ও ম্যাসেজ-টেমপ্লেট
  (কোন সময়ে, কোন ছাত্র, কোন ডিভাইস/লোকেশন থেকে ঢুকল) ঠিক করার জন্য আলাদা
  রাখা হয়েছে, যাতে SMS/wallet-স্পর্শী অংশটা আলাদাভাবে যাচাই করা যায়
  (AGENTS.md protected-path নিয়মের চেতনায়, যদিও sms.js টেকনিক্যালি
  protected-list-এ নেই)।
- **টেস্ট:** `npm run check` + settings পেজ থেকে টাইপ অন/অফ করে ম্যানুয়ালি
  যাচাই যে টগল অনুযায়ী SMS যাচ্ছে/যাচ্ছে না।

### Phase 4 — কিয়স্ক মনিটর UI (ফ্রন্টএন্ড)

- নতুন `client/src/pages/kiosk/Kiosk.tsx`, রুট `/kiosk/:deviceId` —
  `App.tsx`-এ `lazy()` দিয়ে যোগ (বিদ্যমান কোড-স্প্লিটিং প্যাটার্নে), কিন্তু
  এই একটা রুট **authenticated চেক ছাড়া পাবলিক থাকবে** (ট্যাবলেট সবসময়
  লগইন-স্ক্রিনে বসে থাকবে না) — `App.tsx`-এর রাউট-গার্ডিং লজিক দেখে এই
  একটা রুটকে ব্যতিক্রম হিসেবে কীভাবে বসানো হয় সেটা এই ধাপেই ঠিক হবে।
- UI: বড় স্ক্রিনে idle অবস্থায় ঘড়ি/প্রতিষ্ঠানের নাম, পাঞ্চ এলে ছাত্রের ছবি
  (Cloudinary URL — বিদ্যমান `cloudinaryImage.ts`-এর `cloudinaryResize`
  রিইউজ করে ছোট সাইজ আনা হবে) + নাম + ক্লাস/শাখা/রোল + সময়, ২-৩ সেকেন্ড
  পর আবার idle-এ ফেরত। অজানা fingerprintId/cardUid হলে "ছাত্র খুঁজে
  পাওয়া যায়নি" বার্তা।
- ডাটা-সোর্স: Phase 2-এর `GET /api/device/latest-punch/:deviceId`,
  ২ সেকেন্ড পোলিং (ধারা ৩-এর সিদ্ধান্ত অনুযায়ী, WebSocket না)।
- ডিজাইন সিস্টেম: এই পেজেও `style={{...}}` সরাসরি না বসিয়ে
  `components/ui/` বা নতুন `.ds-*`/component-scoped ক্লাস ব্যবহার হবে
  (AGENTS.md-এর mandatory design-system রুল, নতুন ফাইল বলে lint থেকে
  ছাড় নেই)।
- **টেস্ট:** `npm run check` (lint+typecheck+build) + Phase 2-এর টেস্ট-পাঞ্চ
  দিয়ে ম্যানুয়ালি দেখা কিয়স্ক পেজে সঠিক ছাত্র-ইনফো আসছে কিনা।

### Phase 5 — হার্ডওয়্যার bridge/agent (মূল রিপোর বাইরে)

- ব্র্যান্ড/মডেল জানার পর শুরু হবে (ধারা ৩-এ উল্লেখ করা হয়েছে, এখনো জানা
  নেই)। সাধারণ কাঠামো: ছোট Node.js স্ক্রিপ্ট, স্থানীয় নেটওয়ার্কে ডিভাইসের
  push/pull প্রোটোকল বা SDK দিয়ে পাঞ্চ ডাটা রিসিভ করবে, প্রতিটা পাঞ্চ
  Phase 2-এর `POST /api/device/punch`-এ ফরওয়ার্ড করবে (deviceId+secretKey
  সহ, যেটা Phase 2-এর ডিভাইস-ম্যানেজমেন্ট রাউট থেকে অ্যাডমিন জেনারেট করবেন)।
- কার্ড-স্ক্যানার যদি সাধারণ keyboard-emulation RFID রিডার হয়, এই bridge
  নাও লাগতে পারে — কিয়স্ক পেজেই সরাসরি ইনপুট নিয়ে punch API কল করা সম্ভব
  (তখন Phase 4-এই একটা hidden input যোগ হবে, আলাদা bridge লাগবে না)।
- **টেস্ট:** আসল ডিভাইস দিয়ে end-to-end (পাঞ্চ → কিয়স্ক স্ক্রিন → গার্জিয়ান
  SMS → attendance টেবিলে এন্ট্রি) — এই ধাপ পুরোপুরি আপনার হার্ডওয়্যার/
  নেটওয়ার্কের উপর নির্ভরশীল বলে সবচেয়ে বেশি ম্যানুয়াল যাচাই লাগবে।

## ৬. পরবর্তী ধাপ

এই পরিকল্পনা, বিশেষ করে **ধারা ৩-এর ৬টা অ্যাসাম্পশন** (পোলিং বনাম WebSocket,
bridge মূল রিপোর বাইরে, এনরোলমেন্ট ম্যানুয়াল, entry/exit নিয়ম, SMS শুধু
entry-তে, নতুন permission নয়) পড়ে ঠিক থাকলে **"শুরু কর"** বা **"১ নম্বর
থেকে শুরু কর"** লিখুন — Phase 1 দিয়ে শুরু হবে, একবারে এক ধাপ। প্রতিটা ধাপ
শেষে আপনার preference অনুযায়ী শুধু পরিবর্তিত/নতুন ফাইলের zip (E:\ ড্রাইভে
সেভ) + একটাই CMD কমান্ড (এক্সট্র্যাক্ট → npm install (root/client/server)
→ npm run check → পাস করলে commit/push, ফেইল করলে থেমে যাবে) দেওয়া হবে।

Phase 5 (হার্ডওয়্যার bridge) শুরুর আগে ডিভাইসের ব্র্যান্ড/মডেল জানা দরকার
হবে — সেটা তখন জিজ্ঞেস করা হবে, এখনই লাগবে না (Phase 1-4 পুরোপুরি
হার্ডওয়্যার-নিরপেক্ষ)।

কোথাও অ্যাসাম্পশন ভুল মনে হলে, শুরু করার আগে বলে দিলে সেভাবে প্ল্যান
এডজাস্ট করে নেব।
