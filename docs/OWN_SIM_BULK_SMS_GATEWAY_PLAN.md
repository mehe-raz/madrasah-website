# নিজের ফোন/SIM দিয়ে বাল্ক SMS পাঠানোর সিস্টেম — পূর্ণাঙ্গ পরিকল্পনা

## প্রেক্ষাপট ও লক্ষ্য (ব্যবহারকারীর চ্যাট থেকে, 2026-08-13)

বর্তমান SMS সিস্টেম (`server/src/lib/smsSender.js` +
`server/src/lib/smsProviders/bulksmsbd.js`) একটা **পেইড রিসেলার**
(BulkSMSBD) ব্যবহার করে, প্ল্যাটফর্ম-লেভেল env var (`SMS_PROVIDER_API_KEY`)
দিয়ে কনফিগার করা, `sms_wallets`/`sms_transactions` দিয়ে ব্যালেন্স
ট্র্যাক করা হয় — প্রতি SMS-এ টাকা কাটে। এই টাস্কটা **সম্পূর্ণ আলাদা, নতুন,
সমান্তরাল সিস্টেম** — কোনো পেইড রিসেলার/API না, বরং **প্রতিষ্ঠানের মালিকের
নিজের Android ফোন + নিজের SIM কার্ড**কে একটা SMS গেটওয়ে বানিয়ে ফ্রি-তে বাল্ক
SMS পাঠানো (খরচ শুধু ফোনের SIM-এর SMS ব্যালেন্স, কোনো API ফি না)।

ব্যবহারকারীর চাওয়া ফ্লো:
1. একটা পেজে ম্যানুয়ালি নাম + নম্বর সেভ করার ফর্ম (ছাত্র টেবিলের সাথে
   সম্পর্কহীন — সম্পূর্ণ স্বাধীন কন্টাক্ট লিস্ট, যে কাউকে যোগ করা যাবে)।
2. একটা মেসেজ বক্সে বার্তা লিখলে, প্রতিটা কন্টাক্টের নাম দিয়ে সম্বোধন করে
   (personalized) সবাইকে আলাদা আলাদা SMS পাঠানো যাবে।
3. এটা করতে প্রতিষ্ঠানের মালিকের নিজের মোবাইল ফোনকে একটা "SMS গেটওয়ে"
   হিসেবে সংযুক্ত (connect) করতে হবে — সুন্দর, ধাপে-ধাপে নির্দেশিত UI দিয়ে,
   যাতে যেকোনো প্রতিষ্ঠান-মালিক (কোনো টেকনিক্যাল জ্ঞান ছাড়াই) নিজেই করতে
   পারেন।
4. ফোনটা ইন্টারনেটে কানেক্টেড থাকতে হবে, SIM-এ SMS ব্যালেন্স থাকতে হবে —
   এইটুকুই দরকার, কোনো প্রোগ্রামিং/কম্পিউটার লাগবে না।

**ভয়েস কল ব্রডকাস্ট এই প্ল্যানের বাইরে** — আগের চ্যাটে ব্যবহারকারীকে জানানো
হয়েছে যে নিয়মিত Android ফোন + ফ্রি API দিয়ে TTS ভয়েস কল করা বাস্তবে সম্ভব
না (Android 10+ কল-অডিও-ইনজেকশন রেস্ট্রিকশন), এর জন্য আলাদা GSM Voice
Gateway হার্ডওয়্যার লাগবে — সেটা সম্পূর্ণ আলাদা, ভবিষ্যতের একটা টাস্ক হবে,
এই প্ল্যানে ছোঁয়া হয়নি।

## বেছে নেওয়া প্রযুক্তি (এই সেশনে সিদ্ধান্ত, ব্যবহারকারীকে জানানো হয়েছে)

**SMSGate (sms-gate.app, ওপেন-সোর্স, Apache 2.0, github.com/capcom6/android-sms-gateway)**
— নিচের কারণে বেছে নেওয়া হয়েছে:
- সম্পূর্ণ ফ্রি, কোনো রেজিস্ট্রেশন/অ্যাকাউন্ট লাগে না — অ্যাপ ইনস্টল করে
  ভেতরেই username/password সেট করা যায়।
- **Cloud mode** ব্যবহার হবে (Local mode না) — কারণ madrasah-website সার্ভার
  ও প্রতিষ্ঠান-মালিকের ফোন সাধারণত আলাদা নেটওয়ার্কে থাকবে; Cloud mode
  ফোনের নিজের ইন্টারনেট কানেকশন দিয়ে `api.sms-gate.app`-এর মাধ্যমে রিলে
  করে, দুটো ডিভাইস একই WiFi-তে থাকা লাগে না — এটাই ব্যবহারকারীর চাওয়া
  "ফোন ইন্টারনেটে কানেক্টেড থাকলেই হবে" শর্তের সাথে মেলে।
- API: `POST https://api.sms-gate.app/3rdparty/v1/messages`, HTTP Basic
  Auth (username:password, অ্যাপে সেট করা), JSON body:
  ```json
  { "textMessage": { "text": "..." }, "phoneNumbers": ["+8801XXXXXXXXX"] }
  ```
  প্রতিটা রিকোয়েস্টে একাধিক নম্বর পাঠানো যায়, কিন্তু personalization
  (প্রতি নম্বরে আলাদা টেক্সট) দরকার বলে আমাদের সার্ভার প্রতি-কন্টাক্টে
  আলাদা রিকোয়েস্ট পাঠাবে (existing `bulksmsbd.js`-এর single-recipient
  প্যাটার্নের মতোই, `smsSender.js`-এর কমেন্টে এই একই যুক্তি আগেই লেখা আছে)।
- **সতর্কতা (implementation-এর সময় যাচাই করা লাগবে):** এই API
  ডিটেইলগুলো পাবলিক ডকুমেন্টেশন (`docs.sms-gate.app`) থেকে নেওয়া, এই
  sandbox থেকে বাস্তবে কল করে টেস্ট করা যায়নি। Phase 2 বাস্তবায়নের সময়
  `https://docs.sms-gate.app/integration/api/` আবার ভিজিট করে/আসল একটা
  টেস্ট রিকোয়েস্ট পাঠিয়ে এন্ডপয়েন্ট/রেসপন্স শেপ কনফার্ম করে নেওয়া উচিত —
  ঠিক যেভাবে `hardware-bridge/`-এর ADMS dialect অপরীক্ষিত হিসেবে ফ্ল্যাগ
  করা হয়েছিল, একই সততার সাথে এখানেও ফ্ল্যাগ করা হলো।
- এটা `institution_payment_gateways` (bKash self-connect, Phase 8E)-এর
  ঠিক same shape-এর একটা নতুন সমান্তরাল সিস্টেম — **প্রতিটা প্রতিষ্ঠান
  নিজের username/password কানেক্ট করবে** (platform-wide env var না, কারণ
  প্রতিটা প্রতিষ্ঠানের নিজের আলাদা ফোন/SIM)। এই কারণেই এটা বিদ্যমান
  `smsSender.js`/`SMS_PROVIDER_API_KEY` সিস্টেমের সাথে মেশানো হয়নি —
  architecture ভিন্ন (per-tenant DB row বনাম platform env var)।

## নতুন DB স্কিমা (tenant-schema-প্রতি, `server/sql/supabase_schema.sql`)

**Protected path flag (AGENTS.md রুল ৪):** নিচের তিনটা টেবিল
`server/sql/supabase_schema.sql`-এ যোগ করা এই টাস্কেরই অংশ — এই প্ল্যান
ফাইলেই আগে থেকে স্পষ্টভাবে জানানো হচ্ছে, বাস্তবায়নের সময় আলাদা করে
থামতে হবে না।

```sql
-- Phase 1: প্রতিষ্ঠানের নিজের ফোন-গেটওয়ে কানেকশন (bKash gateway টেবিলের প্যাটার্নে)
create table if not exists own_sms_gateway (
  id integer generated by default as identity primary key,
  provider text not null default 'smsgate', -- ভবিষ্যতে অন্য own-device অ্যাপ যোগ হতে পারে
  "usernameEnc" text,
  "passwordEnc" text,
  connected boolean not null default false,
  "lastCheckedAt" text,
  "lastError" text,
  "updatedAt" text
);

-- Phase 1: ম্যানুয়ালি সেভ করা নাম+নম্বর কন্টাক্ট লিস্ট (students টেবিলের সাথে সম্পর্কহীন)
create table if not exists sms_contacts (
  id integer generated by default as identity primary key,
  name text not null,
  phone text not null,
  "groupName" text, -- ঐচ্ছিক ট্যাগ/গ্রুপ, Phase 5-এ UI-তে ফিল্টার করার জন্য
  "createdAt" text not null
);
create index if not exists sms_contacts_group_idx on sms_contacts ("groupName");

-- Phase 1: প্রতিটা বাল্ক-ব্রডকাস্টের হিস্টোরি/লগ
create table if not exists sms_broadcast_logs (
  id integer generated by default as identity primary key,
  "messageTemplate" text not null,
  "recipientCount" integer not null default 0,
  "sentCount" integer not null default 0,
  "failedCount" integer not null default 0,
  "sentBy" integer references users(id) on delete set null,
  "createdAt" text not null
);
```

`own_sms_gateway`-এ কখনো একাধিক রো হবে না (bKash gateway টেবিলের মতোই এক
প্রতিষ্ঠানে এক রো) — কোড-লেভেলে `LIMIT 1` দিয়ে হ্যান্ডল হবে,
`institution_payment_gateways`-এর একই কনভেনশন।

**নতুন প্রতিষ্ঠান** এমনিতেই `tenantProvision.js` এই একই স্কিমা ফাইল পড়ে
বলে অটোমেটিক পাবে। **ইতিমধ্যে বিদ্যমান multi-tenant প্রতিষ্ঠান**-দের জন্য
Super-Admin প্যানেলের "run SQL on all tenants" টুল দিয়ে উপরের তিনটা
`create table` ম্যানুয়ালি রান করা লাগবে (আগের সব নতুন-টেবিল ফিচারের মতোই)।

## Reuse করতে হবে (নতুন করে লেখা যাবে না)

- **`server/src/lib/gatewayCredentialCrypto.js`** — bKash-এর
  AES-256-GCM এনক্রিপশন হেল্পার, একই `GATEWAY_CREDENTIAL_KEY` env var দিয়ে
  username/password এনক্রিপ্ট করতে reuse হবে (নতুন crypto ফাইল লাগবে না)।
- **`server/src/lib/paymentGatewayCredentials.js`**-এর প্যাটার্ন (নতুন
  কপি না, শুধু structure অনুসরণ) — একটা নতুন
  `server/src/lib/ownSmsGatewayCredentials.js` এই একই শেপে বানাতে হবে
  (কানেক্টেড গেটওয়ে ডিক্রিপ্ট করে ফেরত দেয়, শুধু পাঠানোর ঠিক আগে)।
- **`server/src/lib/smsProviders/index.js`**-এর provider-registry
  প্যাটার্ন — নতুন `server/src/lib/smsProviders/smsgate.js` ঠিক
  `bulksmsbd.js`-এর শেপে (`send({...}) -> {ok, providerMessageId, raw}`)
  বানানো হবে, কিন্তু **এটা `smsSender.js`-এর রেজিস্ট্রিতে যোগ হবে না** —
  own-device গেটওয়ে সম্পূর্ণ আলাদা রুট/লজিকে চলবে (নিচে দেখুন), কারণ
  `smsSender.js` প্ল্যাটফর্ম-লেভেল ওয়ালেট-ডিডাক্ট করে, এই ফিচারে কোনো
  ওয়ালেট/ডিডাকশন নেই (নিজের SIM ব্যালেন্স, madrasah-website এর হিসাবের
  বাইরে)।
- **AES এনক্রিপশন/কানেক্ট-ডিসকানেক্ট UI প্যাটার্ন** —
  `client/src/modules/PaymentGatewaySettings.tsx` এই নতুন ফিচারের গেটওয়ে-
  কানেক্ট সেকশনের সবচেয়ে কাছের রেফারেন্স (status card + connect ফর্ম +
  disconnect বাটন)।
- **`requirePermission("settings")` + `requirePlanFeature("sms")`** —
  বিদ্যমান `routes/sms.js`-এর মতোই router-লেভেলে বসবে (একই "sms" প্ল্যান-
  ফিচার রিইউজ, নতুন ফিচার-কী লাগবে না — এটাও SMS-সম্পর্কিত সুবিধা)।

## Phase ভাঙন ও কারণ

7 Phase-এ ভাগ করা হয়েছে — প্রতিটা শেষে repo একটা কাজ-করা, `npm run check`-
যোগ্য স্থিতিশীল অবস্থায় থাকবে (এই কোডবেসের established কনভেনশন)। Backend
(gateway connect → contacts → broadcast) সবসময় সংশ্লিষ্ট frontend-এর আগে,
কারণ frontend টেস্ট করার মতো কিছু থাকতে হলে endpoint আগে রেডি থাকতে হবে।

### Phase 1 — DB স্কিমা + এনক্রিপশন হেল্পার (backend infra, কোনো রুট না)
- উপরের তিনটা `create table` `server/sql/supabase_schema.sql`-এ যোগ
  (protected path, উপরেই ফ্ল্যাগ করা হয়েছে)।
- নতুন `server/src/lib/ownSmsGatewayCredentials.js` —
  `paymentGatewayCredentials.js`-এর শেপে (`getConnectedGateway()`,
  ডিক্রিপ্ট করে `{username, password}` ফেরত দেয় অথবা `null` যদি
  কানেক্টেড না থাকে)।
- নতুন `server/src/lib/smsProviders/smsgate.js` — `send({username,
  password, to, message})` → `POST
  https://api.sms-gate.app/3rdparty/v1/messages`, Basic Auth
  (`Buffer.from(username+":"+password).toString("base64")`), body
  `{textMessage: {text: message}, phoneNumbers: [to]}`. সফল/ব্যর্থ
  response parse করে `{ok, raw}` ফেরত দেয় (কখনো throw করে না, network
  এরর ছাড়া — `bulksmsbd.js`-এর একই কন্ট্রাক্ট)। **উপরের সতর্কতা অনুযায়ী
  আসল রেসপন্স শেপ (success status code/body field নাম) বাস্তবায়নের সময়
  docs.sms-gate.app থেকে আরেকবার কনফার্ম করা।**
- এই ফাজে কোনো `index.js`/রুট ওয়্যারিং হবে না — শুধু বিল্ডিং ব্লক।
- `node --check` দিয়ে সিনট্যাক্স-যাচাই।

### Phase 2 — Backend: গেটওয়ে কানেক্ট/ডিসকানেক্ট/স্ট্যাটাস রুট
- নতুন `server/src/routes/ownSmsGateway.js` (tenant-side,
  `requirePermission("settings")` + `requirePlanFeature("sms")`):
  - `GET /status` — connected/provider/lastCheckedAt/lastError
    (ডিক্রিপ্টেড পাসওয়ার্ড কখনো ফেরত না, `paymentGateway.js`-এর
    `/status`-এর একই কন্ট্রাক্ট)।
  - `POST /connect` — body `{username, password}` → `smsgate.js` দিয়ে
    একটা হালকা টেস্ট রিকোয়েস্ট পাঠিয়ে ভ্যালিডেট (যেমন `GET
    /3rdparty/v1/messages?limit=1` Basic Auth দিয়ে — 200/401 দিয়ে

## গুরুত্বপূর্ণ নকশা-সিদ্ধান্ত (পরের এজেন্ট যেন প্রশ্ন না করে অনুমান করে বদলে না ফেলে)

1. **`sms_wallets`/`sms_transactions` (BulkSMSBD সিস্টেম)-এর সাথে এই
   ফিচার সংযুক্ত না** — সম্পূর্ণ আলাদা টেবিল/রুট/UI। কোনো ব্যালেন্স-
   ডিডাকশন এখানে নেই, কারণ খরচ প্রতিষ্ঠানের নিজের SIM-এ হচ্ছে,
   madrasah-website-এর হিসাবের বাইরে।
2. **`students`/`guardian_students` টেবিলের সাথে `sms_contacts`-এর কোনো
   সম্পর্ক নেই** — এটা সম্পূর্ণ স্বাধীন, ম্যানুয়ালি-সেভ-করা কন্টাক্ট
   লিস্ট, ছাত্র/অভিভাবক ডেটা থেকে অটো-ইমপোর্ট করার কোনো ফিচার এই
   প্ল্যানে নেই (ব্যবহারকারী চাননি — যদি ভবিষ্যতে চান, আলাদা "ছাত্রদের
   থেকে ইমপোর্ট করুন" বাটন যোগ করা যাবে)।
3. **প্রতি-প্রতিষ্ঠান একটাই গেটওয়ে কানেকশন** (`own_sms_gateway`-এ এক
   রো) — মাল্টি-ডিভাইস সাপোর্ট (SMSGate নিজে সাপোর্ট করে) এই প্ল্যানের
   স্কোপে নেই, ভবিষ্যতে চাইলে আলাদা কাজ।
4. **`{নাম}`/`{name}` দুটো প্লেসহোল্ডারই সাপোর্ট করা** (bn/en দুই
   ভাষার ব্যবহারকারীর জন্য) — শুধু একটা রাখলে ভাষা-নির্দিষ্ট হয়ে যেত।
5. প্রোভাইডার হিসেবে SMSGate বেছে নেওয়া হলেও, `smsProviders/smsgate.js`
   ফাইলটা আলাদা রাখা হয়েছে (আগের `bulksmsbd.js`-এর মতোই একটা adapter
   শেপে) — ভবিষ্যতে ব্যবহারকারী অন্য কোনো own-device অ্যাপ (textbee,
   ইত্যাদি) চাইলে শুধু একটা নতুন adapter ফাইল + `own_sms_gateway.provider`
   ভ্যালু বদলালেই চলবে, বাকি রুট/UI কোড অপরিবর্তিত থাকবে (provider-
   agnostic ডিজাইন, `smsProviders/index.js`-এর একই নীতি অনুসরণ করে হলেও
   এই নতুন own-device রেজিস্ট্রি আলাদা ফাইলে/আলাদা রুটে থাকবে, পুরনো
   `smsProviders/index.js`-এ যোগ করা হবে না — কারণ ওটা platform-wide,
   এটা per-tenant)।
